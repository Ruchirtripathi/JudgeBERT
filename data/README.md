# Data Layer

This directory holds the corpus and everything that produces it. Nothing in
here is generated by a model; every file is traceable to an authored batch or
a retrieved source document.

```
data/
├── raw/                     # immutable inputs — never edited by hand
│   ├── sources/             # 8 official statute PDFs (4 English, 4 Hindi)
│   ├── sections/            # per-section JSONL parsed from the English PDFs
│   └── authored/            # 7 hand-authored JSONL batches = the corpus source of truth
├── processed/
│   ├── lmp_pairs.csv        # THE MASTER CORPUS (340 rows x 23 cols)
│   ├── curator_drafts.csv   # CURATOR-ONLY draft scores — never shown to annotators
│   └── build_manifest.json  # what the build produced, and what it refused to
└── annotations/
    ├── annotators/          # one file per annotator — created by the annotation tool
    └── adjudication.csv     # consensus scores — created by the adjudication tab
```

`curator_drafts.csv` lives under `processed/`, deliberately **not** under
`annotations/`. It pairs every `pair_id` with the curator's draft score and the
error type the pair was designed to exhibit, so it is an automatically
generated expected label for the whole corpus. The annotation tool is blind and
never reads it; keeping it out of the annotator-facing directory means an
annotator cannot reach it by browsing the folder they are told to write to.

**The pipeline is a single chain with one direction of flow:**

```
raw/sources/*.pdf ──extract_sources──> raw/sections/*.jsonl ─┐
                                                             ├─> processed/lmp_pairs.csv
raw/authored/*.jsonl ──────────────────build_dataset─────────┘        │
                                                                      │
                       annotations/annotators/*.csv ──merge_annotations─┘
```

## 1. The master corpus: `processed/lmp_pairs.csv`

**340 pairs** — 170 English, 170 Hindi — over three legal domains, drawn from
159 distinct source provisions. Every row is a pair of sentences: an
`original_text` (statutory) and a `simplified_text` (a rewrite of it).

| Property | Value |
| --- | --- |
| Rows | 340 |
| Languages | 170 `en`, 170 `hi` |
| Domains | 202 `contract`, 72 `cyber`, 66 `sale_of_goods` |
| Source groups | 159 (every group contains both languages) |
| Splits | 234 train / 50 validation / 56 test |
| Groups spanning splits | **0** |
| Human annotations | **0** — see §3 |

### The integrity property

This is the most important thing to understand about this file, and the one
easiest to get wrong:

> **`human_lmp_score`, `error_type` and `decision` are empty in all 340 rows.**

They are empty because no human has annotated this corpus yet. A machine
cannot fill them:

| Column | Filled by | Status |
| --- | --- | --- |
| `draft_lmp_score` | the corpus author | 340 rows — **a suggestion, not a label** |
| `draft_error_type` | the corpus author | 340 rows — **a suggestion, not a label** |
| `human_lmp_score` | a human annotator | **0 rows** |
| `error_type` | a human annotator | **0 rows** |
| `decision` | derived from `human_lmp_score` | **0 rows** |

`annotation_status` is `"draft"` for all 340 rows. The gate that enforces this
is `schema.is_gold()`, and any experiment that tries to run on non-gold rows
fails loudly:

```python
>>> from src.data.load_data import load_master, assert_gold
>>> assert_gold(load_master(subset="gold"), "Experiment 1")
ValueError: No rows available for Experiment 1. TODO_HUMAN_ANNOTATION — annotate
the corpus before evaluating.
```

Every column is specified in `src/data/schema.py`, which is the single source
of truth for names, dtypes and permitted values. The block below is generated
from that module — see §6 for how to regenerate it.

### Two columns that look alike and are not

`error_type` and `draft_error_type`; `human_lmp_score` and `draft_lmp_score`.
The `draft_` prefix always means *"a suggestion from the corpus author, not a
judgement"*. Confusing the two is the single most likely way to accidentally
report a fabricated result, so the distinction is enforced in code rather than
left to care.

## 2. `verbatim_quote` — read this before using the Hindi half

| Language | `verbatim_quote` | Meaning |
| --- | --- | --- |
| English (170) | `"true"` | Quoted from the official English PDF; independently checkable |
| Hindi (170) | `"false"` | **Author-rendered**, not machine-read from any Hindi PDF |

The Hindi rows are author-rendered because **every official Hindi statute PDF
obtained for this project uses a legacy non-Unicode font whose glyph mapping
is broken**, so extracted text is not Hindi. The Hindi for "Act" — अधिनियम —
appears zero times in a 41-page Hindi Act. See
[`reports/source_provenance.md`](../reports/source_provenance.md) for the full
evidence, including the proof that the corruption cannot be reversed.

Consequences the paper must state:

* The two language halves are **not equivalent provenance categories** (one
  quoted, one rendered), so a cross-lingual performance gap mixes a language
  effect with a provenance effect. Experiment 2 must say so.
* `verbatim_quote: "false"` records **how the text was obtained, not whether it
  is good Hindi**.
* The Hindi rows are reproducible from `raw/authored/*.jsonl`, but *not* from
  `raw/sources/*_hin.pdf`.

`src/data/build_dataset.py` hard-fails a build in which a Hindi row claims
`verbatim_quote: "true"`, so this cannot be lost by a later edit.

## 3. Annotating the corpus

The corpus is **unannotated**. Experiments cannot be run until it is not. The
infrastructure is complete:

```bash
# 1. Read the guidelines (required before scoring anything)
open src/annotation/guidelines.md

# 2. Run the annotation tool — blind mode is the default
.venv/bin/streamlit run src/annotation/annotation_app.py

# 3. Each annotator scores independently; scores land in
#    data/annotations/annotators/<annotator_id>.csv

# 4. Check agreement (real values only, never estimated)
.venv/bin/python -m src.annotation.agreement --report

# 5. Adjudicate pairs differing by >= 2 points (Adjudicate tab), then merge
.venv/bin/python -m src.annotation.merge_annotations            # dry run
.venv/bin/python -m src.annotation.merge_annotations --apply --backup
```

`merge_annotations` is the **only** thing that may write the master's gold
columns. It stamps `annotation_status`, `annotator_id` and `annotated_at` from
the annotation files, so every label is traceable to a person and a time.
Hand-editing `lmp_pairs.csv` produces a row with no provenance, and validation
will report it.

| Situation | `annotation_status` written | Score written |
| --- | --- | --- |
| an adjudication exists | `human_consensus` | the adjudicated score |
| ≥2 annotators, spread < 2 | `human_consensus` | the mean |
| ≥2 annotators, spread ≥ 2 | `human_multi_pending` | the mean (provisional) |
| exactly 1 annotator | `human_single` | that score |
| no human score | *unchanged* | *unchanged* |

Only `human_consensus` rows should be used for the paper's primary results.
`human_multi_pending` is a human-derived label but not an adjudicated one, and
`merge_annotations` prints how many remain so the distinction cannot be lost.

## 4. Splits, and why they are grouped

`split` is assigned by `src/data/split_data.py` using a greedy largest-remainder
allocator over `language × legal_domain × score_bucket` strata.

**Rows are grouped by `source_group` first and whole groups go to one split.**
This is the primary anti-leakage mechanism. Several provisions appear two,
three or four times in the corpus as different reformulations of the same
sentence; if one sibling landed in train and another in test, the model would
be evaluated on text it had effectively already seen. There are currently
**0 groups spanning multiple splits**.

Determinism: the allocation is seeded from `splits.seed`, so re-running
reproduces the identical assignment.

## 5. Rebuilding from scratch

```bash
# PDFs -> per-section JSONL (English only; the Hindi PDFs are unusable)
.venv/bin/python -m src.data.extract_sources

# authored JSONL -> master CSV + drafts + manifest, with splits assigned
.venv/bin/python -m src.data.build_dataset

# schema, vocabulary, range and leakage checks -> reports/data_quality.md
.venv/bin/python -m src.data.validate_data --write-report

# re-assign splits and write reports/split_diagnostics.md
.venv/bin/python -m src.data.split_data --report
```

`build_dataset` is safe to re-run: it reads only `raw/authored/*.jsonl` and
rewrites the master. It **refuses to write** — via
`assert_no_premature_judgements` — if any gold column would be populated, so a
mistake in the build cannot silently ship a contaminated corpus. Re-running it
therefore cannot destroy human annotation that lives in
`annotations/annotators/`; that is merged back in separately at step 5 of §3.

## 7. Files not to edit by hand

Everything in `raw/` is an input and is treated as immutable. `processed/` is
regenerated by the commands in §5. `annotations/annotators/` and
`annotations/adjudication.csv` are written only by the annotation tool.

The one file a human may reasonably edit is an authored batch in
`raw/authored/`, and only to add or correct pairs — followed by re-running
`build_dataset` and `validate_data`.
